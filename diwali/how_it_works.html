Diwali light show · how it works

How the lights hear the music

A speaker plays a song. A ring of 12 tiny lights flashes along with it. Nothing in the ring can hear. This page shows how a Raspberry Pi turns sound into numbers, and numbers into light.

The big picture

Six steps from song to sparkle

The whole trick is that a song file is just a very long list of numbers. Numbers are something a computer can look at, and something it can use to decide what the lights should do.

Start with a song fileYour firecracker sound began as an MP3. We changed it once, on the Mac, into a WAV file because a WAV is easy for Python to read.
Read the numbers inside the WAVThe WAV is a list of about 1.2 million numbers for each speaker side (left and right) for every 28 seconds of sound. Each number says how far the speaker should push at that instant.
Measure how loud it is, 100 times a secondThe code chops the list into tiny 10 millisecond pieces and gives each piece a loudness score.
Spot the hitsWhen the loudness jumps up fast, that is a bang or a drum hit. The code writes down the exact time of every hit.
Turn each hit into colorsA big bang fills the ring with a color. A small crackle flashes a few random lights. Everything fades out smoothly.
Play the sound and the lights togetherThe sound goes to the speaker. At the same moment, the lights follow the list of hit times, using the same clock.
The speaker and the lights are two separate jobs that start together. The lights never listen to the speaker. They follow a plan that was worked out from the song before it started.
Part 1 · Sound

What sound really is

When a firecracker pops or a drum is hit, the air shakes back and forth very fast. A speaker moves in and out to make the air shake the same way. That back and forth shaking is a sound wave. Drag the sliders and watch the wave change.

Tall wave = loud. A tall wave pushes the air hard. A whisper makes a short wave. The code uses this: loudness is the thing it measures to find the hits.
Packed wave = high pitch. Many wiggles close together sound high and sharp, like a whistle. Slow wiggles sound low and deep, like a big drum.
Part 2 · The WAV file

Turning a wave into numbers

A computer cannot store a smooth wave. It stores snapshots instead. It checks how far the wave is from the middle line, writes down a number, and does this again and again, very fast. A WAV file is exactly that: a long list of snapshot numbers. Try fewer and more snapshots below.

With only a few snapshots, the copy of the wave looks rough and spiky. With lots, it looks smooth. A WAV file made for music takes 44,100 snapshots every second. That is so many that your ears cannot tell it from the real thing.

Real numbers from your firecracker sound

These are 24 snapshots taken straight from fire-cracker-sound.wav, right at the first loud pop. Each bar is one number. Up means the speaker pushes out, down means it pulls in.

That is all of this: 24 numbers, taking about half a thousandth of a second. The whole song has about 1.2 million of them for each side.

Check the math. 28.32 seconds × 44,100 snapshots × 2 channels × 2 bytes = 4,995,648 bytes. That is exactly how big the sound data in the WAV file is, about 5 megabytes. An MP3 squeezes this to under 1 megabyte by throwing away details your ears barely notice. That is why we unpack it into a WAV first.
# diwali_show.py, analyse_wav(): open the WAV and pull out the numbers
with wave.open(path) as w:
    raw = w.readframes(w.getnframes())   # all the snapshot bytes
x = array.array("h")                      # "h" = a list of 2-byte whole numbers
x.frombytes(raw)                          # now x[0], x[1], x[2]... are the snapshots
Part 3 · Listening with math

How the code finds the hits

Now the code has a list of numbers. It needs to find the exciting moments. It does this in two small steps.

Step A. Give every 10 milliseconds a loudness score

The code cuts the list into small pieces that are each 10 thousandths of a second long. (To save time it first skips every other snapshot, so 220 snapshots make one piece.) For each piece it works out how big the wave is. Big wave, big score. The score is then scaled so the loudest piece in the song is 1.0.

Step B. Look for a sudden jump

A bang is not just loud. It gets loud suddenly. So the code keeps a running average of the last 0.4 seconds, the pink line below. When a bar shoots up well above that line, it marks a hit.

These are the real loudness scores for the first 12 seconds of your firecracker sound. Teal dots are detected hits. Slide to a small number and the code gets jumpy and sees hits everywhere. Slide to a big number and it only notices the biggest bangs. The Pi uses 0.06, which finds 50 hits in the full 28 seconds.

Bass or treble?

The code also asks whether each hit is low and boomy or high and sharp. It does this with a simple filter that lets the slow wiggles pass through and catches the fast wiggles separately.

Slow wiggles = bass (a drum thump)
Fast wiggles = treble (a sharp crackle)

The treble-versus-bass number is saved with every hit. The diya style uses it to make sharp hits look more golden.

# The hit rule, in plain Python
avg  = average of the last 0.4 seconds of loudness
rise = loudness_now - max(avg, loudness_just_before)
if rise > 0.06 and it is still going up and 0.07 s have passed since the last hit:
    save the hit: (time, strength, treble_amount)
Part 4 · The lights

How a NeoPixel ring works

Your ring has 12 tiny lights. Each one is really three lights in one: red, green and blue. Each of those can be set from 0 (off) to 255 (full power). Mixing them gives every color: red + green makes yellow, all three at full makes white, all zero is dark.

Light chosen: 0. Click any light on the ring to choose it.
strip[0] = (255, 140, 0)
Memory in the Pi (what the code has written down so far)
Two steps to change a light. First, strip[3] = (255, 140, 0) writes a color into the Pi's memory. Nothing lights up yet. Then strip.show() sends the whole list to the ring in one go. Try it: change a light, see the memory row change, then press strip.show(). This is why the code can paint all 12 lights and make them change at the same instant.

The Pi sends the list of colors down a single wire called SPI. The first light takes its three numbers, passes the rest along, and so on around the ring. The colors arrive in the order green, red, blue, and the code says so with neopixel.GRB. The brightness option in our script simply multiplies every number by 0.5 so the ring is easier on the eyes.

# What every light show script does, from your reference code
spi   = board.SPI()
strip = neopixel.NeoPixel_SPI(spi, 12, pixel_order=neopixel.GRB, auto_write=False)

strip[3] = (255, 140, 0)   # write: light 3 becomes orange (in memory only)
strip.show()               # send: now the ring really changes
Part 5 · Putting it together

From hit times to light patterns

Now we have a list of hits: when each one happened, how strong it was, and whether it was bass or treble. The code walks through that list while the song plays. Press play to watch the real firecracker hits drive the ring. This is the same logic the Pi runs, with the first 12 seconds of the song.

Why do the lights fade out instead of just switching off?

After every frame the code makes each light a little dimmer. It halves the brightness over a short time called the half-life: 0.2 seconds for fireworks, 0.4 for diya, 0.3 for rangoli. A hit makes a light jump to full brightness, then it glides back down. Your eye sees a glowing trail instead of a harsh blink. Without it, the show would look like a flickering mess.

# diwali_show.py, run_file(): the heart of the show (shortened)
while True:
    t = now - start_time                      # how many seconds into the song are we?
    while next_hit_time <= t:                # has a hit's time arrived?
        on_onset(hit)                         # light the ring for that hit
    ring.decay(dt)                            # fade every light a little
    ambient(t, loudness_now)                  # add the between-hits glow
    for i in range(12):
        strip[i] = (r, g, b) * brightness     # write colors to memory
    strip.show()                              # send to the ring
    time.sleep(0.02)                          # 50 times every second
Part 6 · Staying in step

How the sound and lights stay together

Both jobs start at the same moment. The code starts the speaker, then immediately notes the time on the Pi's clock. After that, the lights always ask the clock "how many seconds since we started?" and light whatever hit belongs to that moment. Because the hit times were measured from the song itself, they match the sound.

If they drift. A USB speaker can take a tiny moment to start. If the lights seem early, run with --latency 0.1. That tells the lights to wait a tenth of a second. If the lights seem late, use a negative number like --latency -0.05.

The first three options in the menu work a little differently. There the code does not need to listen at all, because it wrote the music itself. Every note is stored with the exact time it plays, so the same list makes the sound and the lights. Each note lights the pixel that matches its pitch, so a rising tune climbs around the ring.

Cheat sheet

Words to remember

SampleOne snapshot of the wave, stored as a number. A WAV file has 44,100 of them every second.
FrameA little 10 millisecond slice of the song that gets one loudness score.
OnsetThe moment a new sound starts, like a bang or a drum hit. The code finds these.
Bass and trebleLow, slow sounds and high, fast sounds.
RGB / GRBRed, green and blue. The NeoPixel wants them in the order green, red, blue.
SPIThe wire and rules the Pi uses to send colors to the ring.
Half-lifeThe time it takes for a light to fade to half its brightness.
LatencyA small delay. The --latency option lines the lights up with the speaker.
